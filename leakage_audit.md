# Classical-channel leakage audit

Manual trace of everything that crosses the classical channel in each pipeline
variant (`Run`, `RunWinnow`, `RunLDPC`), checked against what `LeakedBits` /
`LeakedBitsTotal` actually account for. Goal: confirm nothing leaks outside
the declared budget that `SecureKeyLength`/`PrivacyAmplify` compresses against.

## Step-by-step trace

**Sifting (`sifting.go`).** Only `PublicEvent` (timestamp, basis, multiphoton
flag) crosses, via `StripBit`/`MatchCoincidences`. The measured `Bit` is never
read until each side indexes its own events at the matched positions. Basis
reconciliation is treated as free, per the standard BBM92/BB84 security
model used here (`SecureKeyLength`'s `1-2*h2(QBER)` rate already assumes a
known-basis sifted key) — not counted in `LeakedBits`, correctly.

**QBER sampling (`qber.go`).** Two call sites:
- `CalculateQBER` (used by `Run`): compares already-discarded blocks (from
  step 2's parity mismatch). Those bits are sacrificed — excluded from
  `Surviving`/fed into privacy amplification — so revealing them in full adds
  nothing to `LeakedBits`'s accounting on purpose: a different position's bit
  value tells Eve nothing about a surviving position (positions are
  independent detection events).
- `siftAndSampleQBER` (used by `RunWinnow`/`RunLDPC`): takes a random
  `sampleFraction` of the sifted key, reveals it fully for comparison, and
  returns only the *remainder* (`aliceRem`/`bobRem`) for correction. Same
  reasoning: sampled bits are excluded from the pool that's hashed, so no
  leak-budget entry is needed. **Minor doc nit**: `WinnowRunResult.LeakedBits`'s
  comment says "QBER sample + Winnow syndromes + CRCs" but the sample
  contributes 0 by design — comment overstates what's counted, worth fixing
  for clarity but not a correctness bug (see Finding 1 below).

**Block error detection (`blockdetect.go`).** Both sides announce parity for
*every* block (`ownParity`/`peerParity` cover all `numBlocks`), but
`ReconcileBlocks` only adds to `LeakedBits` for *kept* blocks
(`if kept[bi] { res.LeakedBits += len(ownParity[bi]) }`). This is correct,
not an undercount: parity is a per-block-local function, so a dropped
block's parity bits say nothing about a kept block's bits, and the dropped
block's own bits never enter `Surviving`. Verified by reading the loop at
`blockdetect.go:303-315`.

**CRC verification (`crcverify.go`).** Same pattern: 16 bits per *kept*
chunk (`res.LeakedBits += 16` only inside the `ok` branch,
`crcverify.go:151-158`). Same reasoning applies — dropped chunks' CRCs don't
bear on surviving chunks, and the chunk's bits themselves go to `Discarded`,
never `Surviving`. CRC collision risk (~1/65536 per chunk) is a residual
*correctness* risk (an errored chunk could slip through as "kept"), already
caught empirically by `TestSplitEndToEndAliceBobIndependentlyAgree` and
`TestPropertySweep` asserting `SurvivingAlice == SurvivingBob` bit-for-bit;
it is not a leakage-accounting bug since the 16 bits announced is an
information-theoretic upper bound on what a 16-bit CRC can reveal regardless.

**Winnow (`winnow.go`, `pipeline_winnow.go`).** Unlike block-detect, nothing
is discarded — Alice's syndrome is announced for *every* block and Bob
corrects toward it. `WinnowPass.LeakedBits = len(aliceSyndrome) *
g.ParityBits()` counts all blocks, which is correct here since all bits
(corrected, not dropped) end up in `Surviving`. `RunWinnow` sums this with
`CRCVerify.LeakedBits` into `res.LeakedBits`, passed straight into
`PrivacyAmplify`. Confirmed no other side-channel value (e.g. per-bit
correction positions, which would leak more than the syndrome bits
themselves) is transmitted or returned to a caller.

**LDPC (`ldpc.go`, `pipeline_ldpc.go`).** Same shape as Winnow: `h.M`
syndrome bits leaked per block, for every block, summed in `LDPCReconcile`
and carried into `res.LeakedBits` identically to the Winnow path.

**Privacy amplification (`privacyamp.go`).** `SecureKeyLength` applies
`rate*n - leakedBits` where `rate = 1 - 2*h2(qber)` (Devetak-Winter / CSS
bound for this protocol's threat model — an asymptotic bound, not a
finite-key correction; worth knowing if this is ever run at small `n`, but
that's a protocol-parameter choice, not a bug). The Toeplitz seed itself is
generated by Alice and sent to Bob in the real deployment; it is public by
design (security lives in accounting for `leakedBits`, not in hiding the
seed) — confirmed by `TestSplitEndToEndAliceBobIndependentlyAgree`, where
Bob only ever receives `seed` and reconstructs the identical key from his
own surviving bits.

## Findings

1. **Doc-only, no behavior change needed**: `WinnowRunResult.LeakedBits`'s
   comment overstates what's counted (says it includes the QBER sample,
   which by design contributes 0). Recommend rewording the comment rather
   than changing behavior, since the current accounting is the *correct*
   one — the sample must stay excluded, not counted.
2. **Operational note, not a code bug**: both CLI binaries
   (`cmd/qoj_post_processing/main.go:527`, `cmd/importtt/main.go:737`) print
   the final secret key as hex to stdout. This is intentional for a
   simulation/inspection tool — both sides' bits are already in one process
   there — but it means terminal scrollback/logs from these commands must be
   treated as key material, not just diagnostic output. Does not apply to
   the split-process deployment model, which never materializes the key for
   display.
3. No undeclared leakage found: every value that crosses the conceptual
   classical-channel boundary (basis/timing, parity, CRC, syndromes, QBER
   sample, Toeplitz seed) is either provably independent of the surviving
   key material, or is correctly summed into the `LeakedBits`/
   `LeakedBitsTotal` figure that `PrivacyAmplify` compresses against.

## What this audit does not cover

Side channels outside the data this library computes on: timing of when
bits are sent over an actual classical network socket, logging/tracing
infrastructure wired up by a caller, or physical-layer attacks on the
quantum channel itself (PNS, detector blinding, etc.) are out of scope for a
post-processing code audit.
